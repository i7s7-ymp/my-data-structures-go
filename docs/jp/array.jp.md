# 静的配列（Array）とは

配列は、同じ型の要素を連続したメモリ領域に格納するデータ構造です。各要素にはインデックス（添字）が割り当てられ、O(1)でランダムアクセスが可能です。

## 静的配列の特徴

- **固定サイズ**: 宣言時にサイズが決まり、実行時に変更不可。Go の場合、配列の長さも一つの情報として扱われ、[1]int と [2]int は異なる型として扱われる
- **ランダムアクセス**: インデックスを用いることで、任意の要素に O(1) で直接アクセスできる。要素がメモリ上に連続で配置されているので、配列自体のアドレス+インデックス\*要素サイズの計算で要素のメモリアドレスを特定できるためである。
- **値のセマンティクス（Go）**: Go 言語の配列(Array)は値型(value type)であり、配列全体が値として扱われる（コピー時は全要素がコピーされる）
- **メモリ効率**: 連続したメモリ領域に格納され、メモリ使用量が予測可能
- **型安全**: コンパイル時に型チェックが行われる

## Go における静的配列

Go の配列は固定長のデータ構造であり、値型として振る舞う。配列の長さは型定義の一部であり、[N]T という型シグネチャを持つ。

この特性から、Go のプログラムで配列 t が用いられることは限定的であり、より柔軟なスライスが一般的によく用いられる。

## 静的配列の用途・注意点

要素数が事前にわかっており、かつ固定の場面と相性が良く、特に組み込みシステムやパフォーマンスが重要なアプリケーションで重宝される。

逆に実行時に要素数を変更する必要がある場面は不向き。

1. **サイズ制限**: 静的配列のサイズは作成時に固定され、実行時に変更できません。
2. **メモリの事前確保**: サイズが決まっているため、使わない領域もメモリを占有する可能性があります。
3. **型の固定性**: 配列のサイズも型の一部となる場合があります
4. **メモリの連続性**: 連続したメモリ領域が必要なため、大きな配列を作成する際にメモリ不足が発生する可能性があります。
5. **挿入・削除のコスト**: 配列の途中に要素を挿入または削除する場合、要素のシフトが必要となり O(n) の計算量が発生します。

# 動的配列とは

実行時にサイズを変更できる配列。

## 動的配列の特徴

- **動的サイズ**: 実行時にサイズを変更可能
- **参照型**: 内部的には配列への参照を持つ
- **メモリ割り当て**: プログラム実行時にヒープ領域からメモリを割り当てることで、実行時の変数に基づいて配列のサイズを決定できる
- **自動リサイズ**: 容量が足りなくなると自動的に拡張される
- **高性能**: 要素追加操作は平均的に O(1)

### メモリ割り当て

ヒープからのメモリ確保は、スタック割り当てに比べて一般的にコストが高い。不要になったメモリはガベージコレクションや手動での解放が必要になる。

### 自動リサイズ

要素を配列に追加して現在の容量を超えると、一般的には以下のプロセスが発生する。

1. 現在の配列よりも大きい、新しいメモリブロックをヒープ上に確保
2. 古い配列の全ての要素を、新しいメモリブロックにコピー
3. 古いメモリブロックを解放（この操作は要素の追加時に時折発生する高コストな処理であり、動的配列のパフォーマンスを議論する上で「償却計算量（amortized analysis）」が重要になる（後述））

### Go における動的配列（スライス）

Go のスライスは動的配列の機能を持っているが、単純な連続したメモリ配列ではなく、既存の配列やスライスの連続した一部分を示す「ビュー」または「ディスクリプタ」になっている。参照型のように振る舞い、変数への代入ではポインタのみがコピーされ、データ本体のコピーは行われない。

スライスは以下の三つの要素で構成される「ヘッダ構造体」として実装されている。

- **ポインタ**: スライスが指し示す基底配列（underlyng array）の最初の要素への参照（ポインタ）
- **長さ(length)**: スライスが現在保持している要素数で、len()関数で取得できる
- **容量(capacity)**: スライスの開始位置から基底配列の末尾までの要素数で、cap()関数で取得できる

長さと容量を分離することで、スライスの効率的な操作が可能になっている。

---

```
基底配列（Underlying Array）
┌────┬────┬────┬────┬────┬────┬────┬────┐
│ 10 │ 20 │ 30 │ 40 │ 50 │ 60 │ 70 │ 80 │
└────┴────┴────┴────┴────┴────┴────┴────┘
  ↑
  │
  └─ ポインタ（ptr）: スライスが指し示す基底配列の開始位置

スライス（例: arr[2:5]）
      ┌─────────────────────────────┐
      │ 30 │ 40 │ 50                │
      └─────────────────────────────┘
        ↑    ↑    ↑
        │    │    │
        └────┴────┴───── 長さ（len）= 3
        └────────────────容量（cap）= 基底配列の先頭から
                             スライス開始位置以降の要素数（この例では6）

【イメージ】
┌────┬────┬────┬────┬────┬────┬────┬────┐
│ 10 │ 20 │[30]│[40]│[50]│ 60 │ 70 │ 80 │
└────┴────┴────┴────┴────┴────┴────┴────┘
            ↑
         ptr（スライスの開始位置）
            │
      ← len=3 →（[30],[40],[50]）
      ←──────────── cap=6 ───────────→（[30],[40],[50],[60],[70],[80]）
```

### Go における append 関数

append はスライスの末尾に要素を追加するための組み込み関数で、スライスの容量に依存して挙動が変化する。

- **容量が十分な場合(len < cap)**: 基底配列の未使用量雨域に新しい要素を書き込み、スライスの len をインクリメントする
- **容量が不足している場合(len >= cap)**: Go のランタイムが新しくより大きい領域に基底配列を確保し、古い基底配列の全要素をコピーし、スライスのポインタを新しい配列に向け直す
  - メモリ使用量とメモリ再確保の頻度とのバランスを取るために最適化されている
  - 一般的に、容量が 1024 未満なら 2 倍、それ以上の場合は約 1.25 倍に拡張される

複数のスライスが同じ基底配列を共有できるが、バグの原因にもなりうる。
あるスライスの一部をスライスとして切り出し、その新しいスライスに append を行うと、基底配列に十分な容量があれば(len < cap)、元のスライスの領域にデータが上書きされてしまう。

- 例: 5 つの要素を持つスライス slice1 を作成
- slice1 のインデックス 1 から 2（値は 20, 30）を切り出して slice2 を作成
- slice2 の長さ（len）は 2 だが、基底配列は slice1 と共有しているため、slice1 の末尾までの容量（cap）を持っている状態になる
- ここで、slice2 に要素 99 を追加
- append を実行すると、slice2 の容量にはまだ空きがあるため、Go は新しい配列を確保せず、基底配列の slice2 のすぐ後ろのメモリ領域（slice1 のインデックス 3 の位置）に 99 を書き込み、slice1 を書き換えてしまう

```go
// 元となるスライスを作成
// len: 5, cap: 5, data: [10 20 30 40 50]
slice1 := []int{10, 20, 30, 40, 50}

// slice1からサブスライスを作成
// slice2はslice1と同じ基底配列を参照する
// len: 2, cap: 4, data: [20 30]
slice2 := slice1[1:3]

// slice2に要素を追加
// slice2のcapにはまだ余裕があるため、新しい配列は確保されない
// 基底配列のslice2の直後の領域に値が書き込まれる
slice2 = append(slice2, 99)

// 結果の確認
fmt.Println("slice1:", slice1) // -> slice1: [10 20 30 99 50]
fmt.Println("slice2:", slice2) // -> slice2: [20 30 99]
```

これを避けるには、append 先の容量を明示的に指定してスライスを切り出すか、copy 関数を利用して新しい基底配列を持つスライスを明示的に作成する方法がある。

## 動的配列の注意点

1. **メモリ再割り当て**: 容量が不足すると新しいメモリ領域を確保してデータをコピーするため、パフォーマンスに影響する場合があります。
2. **メモリ使用量の予測困難**: 動的にサイズが変わるため、メモリ使用量を事前に予測することが困難です。
3. **参照の管理**: 動的配列は参照型である場合が多いため、複数の変数が同じ配列を参照する可能性があります
4. **メモリの連続性**: 連続したメモリ領域が必要なため、大きな配列を作成する際にメモリ不足が発生する可能性があります。
5. **挿入・削除のコスト**: 配列の途中に要素を挿入または削除する場合、要素のシフトが必要となり O(n) の計算量が発生します。

# 実装方法

## 静的配列（Array）

```go
package main

import "fmt"

func main() {
    var staticArray [5]int // サイズが5の静的配列
    staticArray[0] = 10
    staticArray[1] = 20

    fmt.Println(staticArray) // [10 20 0 0 0]
}
```

### 値型の特性

```go
func modifyArray(arr [3]int) {
    arr[0] = 100  // 元の配列は変更されない（コピーが渡される）
}

func main() {
    original := [3]int{1, 2, 3}
    modifyArray(original)
    fmt.Println(original) // [1 2 3] - 変更されない
}
```

### Go 特有の注意点

1. **型の厳密性**: `[3]int` と `[5]int` は完全に異なる型として扱われる
2. **関数渡しのコスト**: 大きな配列を関数に渡すと全要素がコピーされ、パフォーマンスに影響
3. **初期化**: 宣言時に明示的にサイズを指定する必要がある

## 静的配列のカスタム実装

Go の組み込み配列を使用せずに静的配列を実装する場合、固定サイズの構造体を使用します。

```go
package main

import "fmt"

// 静的配列構造体
type StaticArray struct {
    data [5]int
}

func (a *StaticArray) Set(index int, value int) {
    if index >= 0 && index < len(a.data) {
        a.data[index] = value
    }
}

func (a *StaticArray) Get(index int) int {
    if index >= 0 && index < len(a.data) {
        return a.data[index]
    }
    return 0 // エラーハンドリングは省略
}

func main() {
    arr := StaticArray{}
    arr.Set(0, 10)
    arr.Set(1, 20)

    fmt.Println(arr.Get(0)) // 10
    fmt.Println(arr.Get(1)) // 20
}
```

## スライス（Slice）- 動的配列

```go
// 動的サイズのスライス
var slice []int = []int{1, 2, 3, 4, 5}

// インデックスアクセス (O(1))
fmt.Println("インデックス 2 の要素:", slice[2])

// 末尾へ動的に要素追加 (平均 O(1))
slice = append(slice, 6)

// 中間への挿入 (O(n))
index := 2
slice = append(slice[:index], append([]int{99}, slice[index:]...)...)

// 中間からの削除 (O(n))
slice = append(slice[:index], slice[index+1:]...)
```

### 内部構造

```go
// スライスは内部的に以下の構造を持つ
type slice struct {
    ptr unsafe.Pointer // 配列への参照
    len int           // 長さ
    cap int           // 容量
}
```

### 容量（Capacity）の概念

```go
s := make([]int, 3, 5)  // 長さ3、容量5のスライス
fmt.Println(len(s))     // 3
fmt.Println(cap(s))     // 5

// 容量内であれば再割り当てなしで要素追加可能
```

### nil スライスと空スライス

```go
var nilSlice []int              // nil スライス
emptySlice := []int{}           // 空スライス
madeSlice := make([]int, 0)     // make で作成した空スライス

fmt.Println(nilSlice == nil)    // true
fmt.Println(emptySlice == nil)  // false
fmt.Println(madeSlice == nil)   // false
```

### スライスの共有

```go
original := []int{1, 2, 3, 4, 5}
slice1 := original[1:3]  // [2, 3]
slice2 := original[2:4]  // [3, 4]

slice1[1] = 99
fmt.Println(original)    // [1 2 99 4 5] - 元の配列も変更される
fmt.Println(slice2)      // [99 4] - slice2も影響を受ける
```

### append の挙動

```go
s1 := []int{1, 2, 3}
s2 := s1

s1 = append(s1, 4)  // 容量が足りない場合、新しい配列が作成される

// s1とs2が異なる配列を参照する可能性がある
```

### Go 特有の注意点

1. **nil スライスの操作**:

```go
var s []int
s = append(s, 1)  // OK: nil スライスにも append 可能
// s[0] = 1       // パニック: nil スライスにはインデックスアクセス不可
```

2. **スライスの比較**:

```go
s1 := []int{1, 2, 3}
s2 := []int{1, 2, 3}
// fmt.Println(s1 == s2)  // コンパイルエラー: スライスは直接比較できない
fmt.Println(s1 == nil)   // OK: nil との比較は可能
```

3. **メモリリーク**:

```go
func getSmallSlice() []int {
    largeSlice := make([]int, 1000000)
    // 小さな部分だけを返すが、大きな配列への参照が残る
    return largeSlice[:5]  // メモリリークの可能性
}


// 対処法: コピーを作成
func getSmallSliceSafe() []int {
    largeSlice := make([]int, 1000000)
    smallSlice := make([]int, 5)
    copy(smallSlice, largeSlice[:5])
    return smallSlice
}
```

4. **関数への渡し方**:

```go
// スライスを変更する関数
func modifySliceContent(s []int) {
    s[0] = 100  // 元のスライスの内容が変更される
}

func modifySliceLength(s []int) {
    s = append(s, 4)  // 元のスライスの長さは変更されない
}

// スライス自体を変更したい場合はポインタを使用
func modifySliceItself(s *[]int) {
    *s = append(*s, 4)  // 元のスライスの長さも変更される
}
```

### パフォーマンスの考慮事項

1. **append の効率性**:

```go
// 非効率: 容量を考慮しない
s := []int{}
for i := 0; i < 1000; i++ {
    s = append(s, i)  // 何度も再割り当てが発生
}

// 効率的: 事前に容量を確保
s := make([]int, 0, 1000)
for i := 0; i < 1000; i++ {
    s = append(s, i)  // 再割り当てが発生しない
}
```

2. **copy vs append**:

```go
// copy を使用（より効率的）
dst := make([]int, len(src))
copy(dst, src)

// append を使用
dst := append([]int(nil), src...)
```

## 動的配列のカスタム実装

Go のスライスを使用せずに動的配列を実装する場合、内部で配列を管理し、サイズ変更時に新しい配列を作成してコピーします。

```go
package main

import "fmt"

// 動的配列構造体
type DynamicArray struct {
    data []int
    size int
}

func NewDynamicArray() *DynamicArray {
    return &DynamicArray{
        data: make([]int, 0),
    }
}

func (a *DynamicArray) Append(value int) {
    if a.size == len(a.data) {
        newData := make([]int, a.size*2+1) // サイズを2倍に拡張
        copy(newData, a.data)
        a.data = newData
    }
    a.data = append(a.data, value)
    a.size++
}

func (a *DynamicArray) Get(index int) int {
    if index >= 0 && index < a.size {
        return a.data[index]
    }
    return 0 // エラーハンドリングは省略
}

func main() {
    arr := NewDynamicArray()
    arr.Append(10)
    arr.Append(20)

    fmt.Println(arr.Get(0)) // 10
    fmt.Println(arr.Get(1)) // 20
}
```

# 配列の使用場面

| 使用場面                       | 推奨タイプ | 理由                               |
| ------------------------------ | ---------- | ---------------------------------- |
| **固定サイズのデータ**         | 静的配列   | メモリ効率と性能が最適             |
| **行列・ベクトル演算**         | 静的配列   | 数学的計算では固定サイズが一般的   |
| **組み込みシステム**           | 静的配列   | メモリ使用量が予測可能             |
| **リアルタイムシステム**       | 静的配列   | 実行時の性能が予測可能             |
| **高性能計算（HPC）**          | 静的配列   | 最大性能とメモリ効率が重要         |
| **メモリ制約が厳しい環境**     | 静的配列   | 無駄なメモリオーバーヘッドを避ける |
| **可変長データの管理**         | 動的配列   | サイズが実行時に決まる場合         |
| **リスト操作が頻繁**           | 動的配列   | 要素の追加・削除が必要             |
| **ユーザーインプット処理**     | 動的配列   | データ量が事前に分からない         |
| **バッファ・キューの実装**     | 動的配列   | サイズが動的に変化する             |
| **アルゴリズムの中間結果保存** | 動的配列   | 結果のサイズが予測困難             |
| **プロトタイピング・開発初期** | 動的配列   | 柔軟性が開発速度を向上させる       |
